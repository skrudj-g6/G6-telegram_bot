# Архитектура

Модульный монолит в одном репозитории. Вывод и пополнение в v1 обрабатывают сотрудники вручную: кошельков, леджера и платёжных интеграций нет.

```
Игрок ── Telegram ── bot (aiogram 3) ──HTTP, X-Service-Token──▶ backend (FastAPI) ──▶ PostgreSQL
                         │                                          ▲
                       Redis (FSM)                                  │ /admin/v1, JWT
Сотрудник ── браузер ── (Caddy) ── admin (nginx + React) ───────────┘
```

| Каталог | Назначение |
|---|---|
| `backend/` | API, бизнес-логика, миграции Alembic, фоновые задачи, CLI |
| `bot/` | Telegram-бот. Доступа к БД не имеет, всё через `/bot/v1` |
| `admin/` | Админ-панель (Vite, React 18, TypeScript) |
| `legacy/` | Прежний прототип бота, только для справки |
| `deploy/`, `scripts/` | Caddy, бэкап и восстановление |

## Backend

Слои: `api/` (маршруты, проверка прав) → `services/` (бизнес-правила, транзакции) → `models/` (SQLAlchemy 2). Ошибки сервисов — `ServiceError(code)`; API отдаёт `{"detail": {"code": ...}}`, бот и панель показывают текст по коду.

Ключевые решения:
- **Гонки.** Смена статуса — условный `UPDATE ... WHERE status = :ожидаемый` с проверкой числа затронутых строк. Два оператора не возьмут одну заявку; «выполнено» и «отклонено» одновременно не пройдут вместе (тесты на PostgreSQL).
- **Идемпотентность.** Создание заявок идёт с ключом идемпотентности: двойное нажатие не создаёт две заявки.
- **История и аудит.** Каждая смена статуса пишется в таблицу истории; действия сотрудников — в append-only `audit_log` в той же транзакции.
- **Уведомления (outbox).** Запись в `notifications` создаётся в одной транзакции со сменой статуса. Бот забирает пачку (`claim`, аренда 120 с), отправляет и подтверждает. Повторы 1/5/15/60 мин, максимум 5 попыток. Доставка «минимум один раз».
- **Фоновые задачи** (в процессе backend, шаг 30 с): закрытие просроченных заявок (10 мин на чек), удаление чеков старше 7 дней, обновление курса USDT (каждые 5 мин, CoinGecko), очистка старых уведомлений (30 дней).
- **Деньги.** Суммы в целых тенге, округление вниз. Процент клуба со знаком (−50…+50): плюс — бонус, минус — комиссия; значение фиксируется в заявке в момент создания.

## Заявки

- Пополнение: `awaiting_receipt → pending → processing → completed | rejected`; также `cancelled`, `expired`.
- Вывод: `pending → processing → completed | rejected`; также `cancelled`.
- Игрок отменяет, пока заявку не взял оператор. Реквизиты выдаёт платёжка (заглушка в v1); при её отсутствии — `no_requisites_available`.

## Безопасность

- Сотрудники: пароли scrypt, access-токен HS256 на 15 минут (только в памяти страницы), refresh в httpOnly-cookie `SameSite=Strict` на 7 дней с ротацией и обнаружением повторного использования. После 5 неверных паролей вход блокируется на 15 минут.
- Права (RBAC) заданы в коде (`core/permissions.py`): owner и admin — всё; operator — игроки и заявки; finance — только просмотр. Admin управляет только operator и finance. Проверка всегда на backend, панель лишь скрывает кнопки.
- Чеки: JPEG/PNG/PDF до 10 МБ, хранятся 7 дней, выдаются только сотрудникам с правом `receipts.view`, каждый просмотр пишется в аудит.
- Токен бота и секреты только из окружения (`.env` не коммитится), CI ищет токены Telegram в репозитории.
