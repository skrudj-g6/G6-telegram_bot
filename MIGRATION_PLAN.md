## 1. Стратегия

Текущий бот не мигрируется «на месте». Он слишком мал (≈5% ТЗ) и не имеет ни БД, ни backend. План:

1. Построить новый модульный монолит (backend + bot + admin) в монорепозитории.
2. Перенести из старого бота только тексты, сценарий онбординга, изображения и идею проверки ID.
3. Старый код оставить в `legacy/` (или в отдельной git-ветке) до выхода v1.0, затем удалить.
4. Данных для миграции нет: старое хранилище — in-memory, при перезапуске оно теряется. **Миграция данных не требуется.**

## 2. Целевая структура репозитория

```
altyn-crown/
├── backend/                 # FastAPI, SQLAlchemy 2, Alembic
│   ├── app/
│   │   ├── core/            # config, security, logging, deps
│   │   ├── db/              # engine, session, base
│   │   ├── models/          # users, poker_accounts, clubs, requests, staff, rbac, audit, notifications
│   │   ├── schemas/         # Pydantic
│   │   ├── services/        # бизнес-логика (заявки, статусы, аудит, уведомления)
│   │   ├── api/
│   │   │   ├── bot/         # внутренний API для бота (service-token)
│   │   │   └── admin/       # API админ-панели (JWT + RBAC)
│   │   └── main.py
│   ├── alembic/
│   ├── tests/
│   └── Dockerfile
├── bot/                     # aiogram 3, тонкий клиент backend
│   ├── app/{handlers,keyboards,states,middlewares,api_client,texts,config}.py
│   └── Dockerfile
├── admin/                   # React + TypeScript (Vite)
├── legacy/                  # старый бот, только для справки
├── docker-compose.yml
├── .env.example
├── .gitignore
└── docs/                    # README, ARCHITECTURE, API, DEPLOY_VPS, BACKUP
```

Модульный монолит: один backend-процесс, один бот-процесс, одна админка, одна PostgreSQL. Без микросервисов.

## 3. Предлагаемые архитектурные решения (требуют согласования)

| # | Решение | Обоснование |
|---|---|---|
| D-1 | **Монорепозиторий** (backend / bot / admin) | Один PR на сквозную фичу, общий docker-compose. |
| D-2 | **Бот не имеет доступа к БД**, только к backend API | Требование ТЗ §3. |
| D-3 | **Доверие к Telegram ID.** Бот — доверенный сервис. Он аутентифицируется на backend секретным service-token (заголовок + опционально HMAC подписи тела). Backend принимает `telegram_id` только от аутентифицированного бота. Бот берёт ID исключительно из update, пришедшего от Telegram (long polling по токену бота или webhook с `secret_token`). Публичный доступ к bot-API закрыт (внутренняя docker-сеть). | Выполняет требование ТЗ §13: ID не принимается от произвольного клиента. |
| D-4 | **Админ-аутентификация:** логин/пароль (argon2/bcrypt) + короткоживущий access JWT + refresh в httpOnly-cookie; rate-limit на вход. | Стандартная безопасная схема для веб-панели. |
| D-5 | **Единая таблица статусов и общая логика заявок** для пополнений и выводов (раздельные таблицы `deposit_requests`/`withdrawal_requests` по ТЗ §11, общий сервис переходов статусов). | Соответствует ТЗ, но без дублирования кода. |
| D-6 | **Защита от гонок:** смена статуса через условный `UPDATE ... WHERE id=:id AND status=:expected` (или `SELECT ... FOR UPDATE`) + проверка числа затронутых строк; колонка `version`. | Требование ТЗ §14: два оператора не берут одну заявку. |
| D-7 | **Идемпотентность:** повторное подтверждение возвращает текущее состояние без побочных эффектов; уникальный `idempotency_key` для создания заявки из бота. | ТЗ §7, §13. |
| D-8 | **Уведомления через outbox:** запись в `notifications` в той же транзакции, что и смена статуса; отдельный воркер отправляет в Telegram с ретраями. Сбой отправки не откатывает заявку. | ТЗ §10. |
| D-9 | **Реквизиты выплат** шифруются на уровне приложения (Fernet/AES-GCM, ключ в ENV), доступ — по отдельному праву, в логи не попадают, маскируются в списках. | ТЗ §6, §13. |
| D-10 | **Суммы:** `BIGINT` в целых тенге, `CHECK (amount >= 3000)` для депозита. | ТЗ §2. |
| D-11 | **Аудит append-only:** в приложении нет UPDATE/DELETE для `audit_logs`; при желании — отдельная БД-роль без этих прав. | ТЗ §8.6. |
| D-12 | **Состояния диалога бота — aiogram FSM** с Redis-хранилищем (один дополнительный контейнер), чтобы диалоги переживали перезапуск. Альтернатива без Redis — хранить состояние в PostgreSQL. Решение — вопрос Q-15. | Текущий бот теряет состояние при перезапуске (B-4). |
| D-13 | **Конфиг:** `pydantic-settings`, все секреты и часовой пояс в ENV. | ТЗ §3, §13. |
| D-14 | **Отмена заявки игроком** разрешена только в `pending`. | Предложение; уточнить Q-5. |

Отклонения от ТЗ: добавление Redis (опционально, D-12) и таблиц `request_status_history`, `request_assignments`, `staff_sessions` — допускается ТЗ §11 («при необходимости добавить отдельные таблицы»).

## 6. Открытые вопросы (нужны бизнес-ответы)

**Игроки и аккаунты**
- Q-1. Один игрок может иметь несколько игровых ID? (ТЗ говорит «привязанные аккаунты» — подтвердить, есть ли лимит.)
- Q-2. Ветка «Крипто» и выбор «страны» из текущего бота: убрать или оставить? ТЗ про них молчит. Если оставить — какие это способы оплаты и как они учитываются в заявке?
- Q-3. Нужна ли проверка членства в клубе 692609 вручную до разрешения заявок? Сейчас шаг «Вступить в клуб» — только ссылка, подтверждения нет.
- Q-4. Что означает «Регистрация в кассе» в текущем бизнес-процессе? Это то же, что привязка ID, или отдельный шаг одобрения сотрудником? Должен ли новый игрок быть `active` сразу или после подтверждения?

**Заявки**
- Q-5. Когда игрок может отменить заявку (только `pending` или и `processing`)?
- Q-6. Максимальная сумма пополнения/вывода? Минимум для вывода (в ТЗ указан только для депозита)? Лимиты по числу открытых заявок на игрока?
- Q-7. Какие именно **реквизиты для выплаты** запрашивать (номер карты Kaspi/Halyk, телефон, IBAN, крипто-адрес)? Нужна ли валидация формата, можно ли сохранять реквизиты в профиль для повторного использования?
- Q-8. Нужна ли у депозита информация, куда игрок отправил деньги (чек, скриншот, комментарий)? Реквизиты клуба для приёма платежа показывает бот — какие и где хранятся? (ТЗ говорит про «дополнительную информацию, если требуется».)
- Q-9. SLA и автозакрытие: что делать с заявкой, которая висит в `pending`/`processing` слишком долго?

**Staff и права**
- Q-10. Точная матрица прав по ролям Owner/Admin/Operator/Finance (особенно: кто видит реквизиты; может ли Operator видеть чужие заявки; может ли Admin управлять Admin'ами).
- Q-11. Может ли один и тот же сотрудник и взять заявку, и подтвердить её, или нужен принцип «четырёх глаз» для выводов выше порога?
- Q-12. Двухфакторная аутентификация для staff — нужна в v1.0?
- Q-13. Механизм «безопасного сброса доступа»: через email, через одноразовую ссылку от Owner, через Telegram?

**Уведомления**
- Q-14. Куда приходят уведомления операторам — в личные сообщения Telegram, в служебный чат/канал, в админку (или всё вместе)? Нужен ли Telegram ID у каждого сотрудника?

**Инфраструктура**
- Q-15. Redis допустим для хранения FSM-состояний бота (D-12)? Если нет — храним в PostgreSQL.
- Q-16. Режим работы бота в production: long polling или webhook (потребуется домен и HTTPS)? Есть ли домен для админки?
- Q-17. Параметры VPS (ОС, ресурсы) и политика бэкапов (частота, срок хранения, куда копируем).
- Q-18. Часовой пояс по умолчанию (например, `Asia/Almaty`).
- Q-19. Нужны ли история/архив для данных старого бота? (Предполагается, что нет, т.к. хранилище в памяти.)
- Q-20. Куда делся `legacy`-бот: оставить в работе до готовности v1.0 или остановить? Работает ли он сейчас с реальными игроками?
