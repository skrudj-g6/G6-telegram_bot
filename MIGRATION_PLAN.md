## 1. Стратегия

Текущий бот не мигрируется «на месте». Он слишком мал (≈5% ТЗ) и не имеет ни БД, ни backend. План:

1. Построить новый модульный монолит (backend + bot + admin) в монорепозитории.
2. Перенести из старого бота только тексты, сценарий онбординга, изображения и идею проверки ID.
3. Старый код оставить в `legacy/` (или в отдельной git-ветке) до выхода v1.0, затем удалить.
4. Данных для миграции нет: старое хранилище — in-memory, при перезапуске оно теряется. **Миграция данных не требуется.**

## 2. Целевая структура репозитория

```
altyn-crown/
├── backend/                 # FastAPI, SQLAlchemy 2, Alembic
│   ├── app/
│   │   ├── core/            # config, security, logging, deps
│   │   ├── db/              # engine, session, base
│   │   ├── models/          # users, poker_accounts, clubs, requests, staff, rbac, audit, notifications
│   │   ├── schemas/         # Pydantic
│   │   ├── services/        # бизнес-логика (заявки, статусы, аудит, уведомления)
│   │   ├── api/
│   │   │   ├── bot/         # внутренний API для бота (service-token)
│   │   │   └── admin/       # API админ-панели (JWT + RBAC)
│   │   └── main.py
│   ├── alembic/
│   ├── tests/
│   └── Dockerfile
├── bot/                     # aiogram 3, тонкий клиент backend
│   ├── app/{handlers,keyboards,states,middlewares,api_client,texts,config}.py
│   └── Dockerfile
├── admin/                   # React + TypeScript (Vite)
├── legacy/                  # старый бот, только для справки
├── docker-compose.yml
├── .env.example
├── .gitignore
└── docs/                    # README, ARCHITECTURE, API, DEPLOY_VPS, BACKUP
```

Модульный монолит: один backend-процесс, один бот-процесс, одна админка, одна PostgreSQL. Без микросервисов.

### 8.2. Реализовано в этапе 2 по этим ответам

- Таблицы `clubs` (с клубом `692609`), `users`, `poker_accounts`; миграция `0002`.
- Регистрация по Telegram ID (идемпотентная, повторный `/start` ничего не дублирует).
- Привязка игрового ID (формат `XXXX-XXXX`, только ASCII-цифры), модерация `pending → approved / rejected`.
  - Пока аккаунт `pending`, игрок может исправить ID (опечатка). После `approved` игрок изменить его не может.
  - После `rejected` игрок может отправить исправленный ID повторно (аккаунт снова `pending`).
- Внутренний API для бота `/bot/v1/...` с service-token (D-3). Telegram ID принимается только от аутентифицированного бота.
- Функции подтверждения/отклонения аккаунта реализованы в сервисе и покрыты тестами (условный `UPDATE`, защита от двойного подтверждения). **HTTP-эндпоинтов для админа пока нет:** они появятся на этапе 5 вместе с авторизацией сотрудников, иначе подтверждение было бы без авторизации.

### 8.3. Отклонения от ТЗ (прошу подтвердить)

1. **Лимиты 1000…2 000 000 KZT настраиваются в панели** (ТЗ: минимум 3000). Хранение: `app_settings`.
2. **Реквизиты от платёжки.** ТЗ §12 запрещает интеграции с платёжными системами. Интеграция остаётся вне v1: в заявке только поле `payment_details`. Предложение на период до подключения платёжки — реквизиты по способам (`fiat`, `crypto`) задаются в панели и копируются в заявку при создании. См. Q-22.
3. **Чек и автозакрытие.** ТЗ §7 знает статусы `pending, processing, completed, rejected, cancelled`. Предлагаю добавить два:
   - `awaiting_receipt` — реквизиты выданы, ждём чек (10 минут);
   - `expired` — закрыта по таймеру без чека.
   Цепочка: `awaiting_receipt → pending (чек получен, в очереди оператора) → processing → completed / rejected`; из `awaiting_receipt` также `cancelled` (игрок) и `expired` (таймер). Нужен фоновый обработчик таймера и хранение файлов чеков (Q-23).
4. **Модерация игрока админом** (Q-3/Q-4) — новый шаг, которого нет в ТЗ §4.2–4.3.
5. **Нет Telegram-уведомлений сотрудникам** (Q-14): в ТЗ §10 они были.
6. **Redis** в docker-compose (Q-15) — добавится на этапе 6.
